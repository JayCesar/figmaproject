No projeto que fiz, não existe possibilidade de o usuário inserir um prompt malicioso, pois não há uma interface que coleta informações do usuário — o input é um CSV de logística gerado internamente e depositado no S3 via processo automatizado. Porém, caso houvesse essa superfície de ataque, as verificações que eu aplicaria seriam:
	1.	Separação estrutural entre instrução e dado — nunca concatenar o conteúdo do arquivo direto na string do prompt de sistema. Usar delimitadores claros (ex: XML tags ou JSON schema) deixando explícito pro modelo o que é instrução fixa e o que é dado do usuário, tratando o conteúdo do arquivo sempre como dado, nunca como comando.
	2.	Sanitização/validação de schema antes da chamada — validar que o CSV segue o schema esperado (colunas, tipos, tamanho de campo) antes de sequer montar o prompt. Qualquer linha fora do padrão é rejeitada ou logada como suspeita, sem chegar na LLM.
	3.	Limite de tamanho e caracteres de controle — truncar/rejeitar campos com tamanho anômalo ou presença de padrões suspeitos (ex: “ignore previous instructions”, tentativas de fechamento de tags, sequências de escape).
	4.	Structured output / function calling — forçar a resposta do Llama num formato estruturado (JSON com schema fixo) em vez de texto livre, reduzindo a superfície de “sequestro” da resposta.
	5.	Least privilege na Lambda — mesmo que o prompt fosse comprometido, a Lambda não tem permissão de IAM pra nada além de ler do bucket de entrada, escrever no MySQL/RDS e no bucket de saída — não teria como o modelo “instruir” a Lambda a fazer algo fora desse escopo, já que a lógica de execução não é ditada pelo output do LLM.
	6.	Logging e alertas — qualquer rejeição de input suspeito é logada no CloudWatch com alerta, pra rastreabilidade.
